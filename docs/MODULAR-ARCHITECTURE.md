# Микросервисная архитектура и сервисный слой

Состояние: 12 сентября 2026 года. Четыре отдельно запускаемых сервиса связаны
сетевыми интерфейсами. Сервис миссий и сервис телеметрии больше не используют
каталог симулятора. Docker и новый общий launcher в эту работу не входят.

## Сервисы и владение данными

| Сервис | Команда | Порт | Зависимости и данные |
| --- | --- | --- | --- |
| Planning | `npm run service:planning` | 9003 | Собственный native solver; чистая библиотека `shared/planning` |
| Missions / route | `npm run service:route` | 9002 | HTTP-клиент шлюза; собственная SQLite-база в `MISSION_STATE_DIR` |
| Telemetry | `npm run service:telemetry` | 9001 | HTTP-клиент шлюза; последняя телеметрия в памяти |
| Webots gateway | `npm run service:gateway` | 9004 | Только здесь файловый адаптер Webots и журнал команд |

`src/features/planner` отвечает за редактор и клиентские сценарии.
`shared/planning` содержит расчёты без React, сети или файловой системы.
`bridge/services` содержит прикладные сценарии с внедрёнными портами.
`bridge/servers` реализует транспорт, а `bridge/processes` собирает зависимости.
`bridge/adapters` реализует сетевые и файловые интерфейсы.
`bridge/repositories` содержит реализации хранилищ. Направление зависимостей
проверяется тестами; фасады прежних frontend-импортов сохранены.

Это сервисы одного репозитория с общим пакетом контрактов и расчётов. Их можно
запускать на разных узлах: между ними не нужен общий файловый каталог. На узле
шлюза остаётся локальный файловый обмен с Webots. Нативный solver устанавливается
на узле planning-сервиса. Это не кластер высокой доступности и не планировщик
парка роботов: текущая конфигурация управляет одним роботом.

## Поток миссии

1. UI передаёт снимок сцены planning-сервису: зоны, покрытия, зарядки и параметры
   движения. Черновики зон исключаются. Сервер строит полный маршрут и возвращает
   `seedRoute`, `route`, `planning`, `scene`, `sceneRevision`.
2. Сервис миссий повторно проверяет маршрут по снимку, сохраняет `prepared` в
   собственной базе и передаёт команду шлюзу. У каждой команды устойчивый ID.
3. Шлюз сохраняет намерение в журнале, записывает сцену и маршрут, затем отмечает
   доставку. Повтор того же запроса возвращает прежний ответ без нового запуска.
4. После ответа шлюза миссия получает `persisted`: это подтверждение записи,
   а не движения. Контроллер возвращает `navigation.missionId`.
5. Фоновый процесс сервиса миссий сверяет обратную связь раз в секунду. UI не
   требуется для сохранения `accepted`, `running`, `completed`, `failed`, `cancelled`.
6. После перезапуска сервиса записи `prepared` повторяются с прежним ID; запросы
   отмены восстанавливаются. Шлюз также сохраняет конечную обратную связь, чтобы
   короткое отключение сервиса миссий не потеряло завершение.

Один робот принимает одну активную миссию. Попытка замены получает 409
`mission_active` или `robot_busy`. После завершения либо подтверждённой отмены
можно отправлять новую. Изменения сцены блокируются на сервисной стороне, пока
миссия активна. UI восстанавливает отслеживание активной миссии через API истории.

## Отмена

`POST /api/missions/:id/cancel` сохраняет намерение `cancelling`. Даже если шлюз
недоступен, намерение остаётся в базе и повторяется фоновым процессом.
Шлюз записывает адресную команду `cancel_mission` в журнал команд контроллера.
Контроллер проверяет ID, останавливает текущую миссию и публикует
`mission_cancelled`. Только тогда сервис возвращает `cancelled`.

Повтор отмены идемпотентен. Старая команда отмены не останавливает другой ID.
Если симулятор выключен или стоит на паузе, подтверждение остановки не выдумывается:
миссия остаётся `cancelling`. Это обычная команда отмены, не аппаратная аварийная
остановка. При перезапуске самого контроллера старый маршрут автоматически не
запускается: сохранение сервисных записей не означает восстановление движения.

## API и контракты

| Интерфейс | Назначение |
| --- | --- |
| Planning `POST /api/solve-route` | Полное планирование; общий `planning.request` / `planning.result` контракт |
| Missions WebSocket `/ui` | Общий `route.command`, ответ `route.ack` с `requestId`, `ok`, статусом или кодом ошибки |
| Missions `GET /api/missions` | История и активная миссия; без исходной команды и внутренних fingerprint |
| Missions `GET /api/missions/:id` | Состояние, отметка времени обратной связи, свежесть и ошибка соединения |
| Missions `POST /api/missions/:id/cancel` | Запрос отмены, HTTP 202 |
| Telemetry WebSocket | Существующий общий контракт телеметрии |
| Gateway `POST /v1/commands` | Версионированные `submit`, `update`, `cancel` |
| Gateway `GET /v1/feedback/:id` | Обратная связь для конкретной миссии |
| Gateway `GET /v1/telemetry` | Последний кадр, ревизия и свежесть |
| Все сервисы `GET /health`, `GET /ready` | Живость и готовность зависимостей |

Запрос команды шлюзу: `{version:1, operation, requestId, payload}`.
Успех: `{version:1, ok:true, payload}`. Ошибка:
`{version:1, ok:false, code, error}` с соответствующим HTTP-статусом.
Неизвестная версия отклоняется до побочных эффектов. Другой payload с прежним ID
даёт 409. Клиент ограничивает время одного запроса тремя секундами и повторяет
временный сбой один раз с тем же ID. Ошибки 4xx не повторяются автоматически.
Фоновое восстановление миссии продолжает попытки после восстановления шлюза.

`/ready` missions и telemetry проверяет шлюз; planning проверяет наличие solver;
шлюз проверяет своё хранилище и каталог обмена. Готовность процесса не означает,
что робот движется или что телеметрия свежая. Файлы обратной связи старше пяти
секунд не считаются свежими; сохранённый конечный результат может возвращаться
из журнала с признаком `cached`.

## Конфигурация и локальный запуск

Нужен Node.js 22.19+; SQLite предоставляется встроенным `node:sqlite` без внешнего
сервера БД. В Node.js 22 этот API выдаёт ExperimentalWarning; это предупреждение
среды Node, а не ошибка сборки C-контроллера.

Собрать компоненты: `npm install`, `npm run native:build`, `npm run webots:build`.
Далее запустить четыре команды из таблицы, `npm run dev`, открыть мир
`webots/worlds/youbot_only.wbt` и включить симуляцию.
Прежний `npm run bridge` сохранён и собирает те же четыре сервиса локально.
Не запускайте оба варианта одновременно на одинаковых портах.

Переменные:

- `GATEWAY_URL` — независимый HTTP(S)-адрес шлюза для missions и telemetry.
- `GATEWAY_BIND_HOST`, `GATEWAY_PORT` — адрес шлюза; по умолчанию loopback:9004.
- `GATEWAY_TOKEN` — общий токен межсервисного доступа. Обязателен для шлюза,
  слушающего не loopback. На недоверенной сети используйте HTTPS через инфраструктуру.
- `ROUTE_BIND_HOST`, `TELEMETRY_BIND_HOST`, `SOLVER_BIND_HOST` — отдельные адреса
  прослушивания; порты `ROUTE_PORT`, `TELEMETRY_PORT`, `SOLVER_PORT`.
- `MISSION_STATE_DIR` — частная база missions, по умолчанию `data/missions`.
- `WEB_STATE_DIR` — только узел шлюза/Webots; внутри `gateway-journal` хранится
  журнал доставки. Сам Webots должен получить то же значение переменной.
- `SOLVER_PATH` — исполняемый файл на узле planning.
- `VITE_PLANNING_URL`, `VITE_MISSION_URL`, `VITE_ROUTE_URL`, `VITE_TELEMETRY_URL` —
  независимые адреса сервисов для браузера; прежние переменные портов поддерживаются.

Для миграции старых JSON-миссий остановите сервис, скопируйте
`web_state/missions/*.json` в `MISSION_STATE_DIR` и запустите сервис. JSON
импортируется в SQLite один раз по ID, исходные файлы сохраняются.
SQLite запрещает двух владельцев одного каталога на одном хосте; после аварийного
завершения локального владельца новый процесс может забрать владение транзакционно.
Базы не предназначены для общего сетевого диска. Один gateway должен владеть
одним каталогом симулятора. Для нескольких роботов нужны отдельные экземпляры
и каталоги. Автоматическая очистка истории пока не включена.

## Проверки

- `npm test`, `npm run lint`, `npm run build` — JS, границы модулей, UI.
- `npm run test:services` — четыре отдельных процесса, настоящие расчёты,
  раздельные каталоги, отказы шлюза, рестарты, повторные запросы, отмена.
  Обратная связь контроллера в этом тесте синтетическая.
- `npm run test:webots` — регрессионные тесты C-контроллера.
- `npm run test:simulation` — Windows/Webots: временная копия мира и контроллера,
  реальное прохождение маршрута, отмена второй миссии и проверка остановки.
  Требует заранее собранных solver и контроллера; использует случайные порты и
  собственные процессы. Итог записывается в `output/physics-smoke-result.json`.

Физический прогон выявил прежнее расхождение допуска положения и порога финального
поворота. Оно устранено: выравнивание конечного курса начинается в пределах
допуска достижения точки. Сервисный слой не маскирует незавершённое движение
статусом успеха.
