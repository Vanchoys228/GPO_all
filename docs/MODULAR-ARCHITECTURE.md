# Модульная архитектура и сервисный слой

Состояние реализации: 8 сентября 2026 года. Приложение сохраняет локальный запуск,
но расчёты, сценарии приложения и инфраструктура имеют отдельные границы.

## Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| `shared/planning/` | Чистые расчёты геометрии, обхода зон, энергии и зарядок. Работают в браузере и обычном Node.js без React, DOM и серверных адаптеров. |
| `src/features/planner/` | Редактирование сцены, предварительный расчёт, запросы планирования и миссий, отображение телеметрии. |
| `bridge/services/planning-service.cjs` | Порядок посещения через внедрённый native solver и полный расчёт маршрута по снимку сцены. |
| `bridge/services/route-planning.cjs` | Проверка сцены, обход препятствий, энергетическая осуществимость и нормализация маршрута для контроллера. |
| `bridge/services/mission-service.cjs` | Идентичность команды, повторные запросы, сохранение миссии и переходы состояния по обратной связи. |
| `bridge/services/route-service.cjs` | Диспетчеризация команд миссии и остальных команд симулятора. |
| `bridge/services/telemetry-service.cjs` | Доставка телеметрии подписчикам через внедрённые зависимости. |
| `bridge/adapters/` | Реализация интерфейсов симулятора через файлы Webots и источник телеметрии. |
| `bridge/repositories/` | JSON-хранилище миссий с атомарной заменой отдельного файла. |
| `bridge/servers/` | HTTP/WebSocket, проверка Origin, упаковка ответов и ошибок. |
| `bridge/processes/` | Сборка зависимостей, отдельные точки запуска и завершение процессов. |

Направление зависимостей: интерфейс и серверные сервисы используют общий расчётный
модуль; сервис миссий получает хранилище и адаптер через аргументы конструктора.
Сервисный слой не импортирует файловую систему, HTTP/WebSocket-серверы или конкретные
адаптеры. Это ограничение проверяется тестами границ.
Старые импорты расчётов в `src/lib` и `src/features/planner/model` сохранены как
фасады совместимости; реализация находится в `shared/planning`.

## Поток планирования и исполнения

1. UI собирает снимок: замкнутые запрещённые зоны и покрытия, зарядки, скорость,
   нагрузка и запас энергии. Незавершённые зоны покрытия остаются черновиками UI.
2. Planning API вычисляет порядок посещения и окончательный маршрут с обходами
   и зарядками. Ответ содержит исходный порядок `seedRoute`, итоговый `route`,
   результат `planning`, нормализованный `scene` и SHA-256 `sceneRevision`.
3. При отправке миссии сервер повторно рассчитывает маршрут по переданному снимку.
   Браузерный предварительный расчёт не заменяет серверную проверку.
4. Сервис сохраняет запись `prepared`, затем передаёт команду адаптеру и сохраняет
   `persisted`. Подтверждение WebSocket содержит идентификатор миссии.
5. Адаптер записывает сцену и маршрут для Webots. Контроллер возвращает тот же
   `commandId` в поле `navigation.missionId` телеметрии.
6. UI опрашивает Mission API. Состояние исполнения меняется только по обратной
   связи с совпадающим идентификатором. Сохранение команды не запускает таймер движения.

Старые запросы планирования без `scene` и существующие служебные команды поддержаны
для совместимости. Полный серверный расчёт требует снимка сцены.

## Интерфейсы инфраструктуры

- Хранилище: `ready()`, `get(missionId)`, `save(record)`.
- Адаптер симулятора: `submit(command)`, `update(payload)`, `getFeedback(missionId)`.
- Сервис миссий: `submit(payload, { requestId })`, `get(missionId)`, `drain()`.
- Корень route-процесса принимает фабрики `createSimulatorAdapter` и
  `createMissionRepository`. Замена транспорта симулятора или хранилища выполняется
  здесь без переноса инфраструктурных импортов в сервис миссий.

Повтор запроса с тем же `requestId` и содержимым возвращает сохранённую миссию;
другое содержимое с тем же ID даёт конфликт 409. При неопределённом результате
доставки запись `prepared` можно повторить с тем же ID: адаптер повторно использует
`commandId`. Контроллер не должен воспринимать такую команду как новый запуск.
Чтобы воспользоваться идемпотентностью после сетевой ошибки, клиент должен сохранить
ID запроса; новое нажатие отправки в UI создаёт новую миссию.

## Запуск и диагностика

Общий запуск: `npm run bridge`, затем `npm run dev`.
Отдельный запуск в трёх терминалах:

```text
npm run service:planning
npm run service:route
npm run service:telemetry
```

| Сервис | Порт по умолчанию | Интерфейсы |
| --- | --- | --- |
| Planning | 9003 | POST `/api/solve-route`, GET `/health`, GET `/ready` |
| Missions / route | 9002 | WebSocket `/ui`, GET `/api/missions/:id`, GET `/health`, GET `/ready` |
| Telemetry | 9001 | WebSocket, GET `/health`, GET `/ready` |

Адрес прослушивания: `BRIDGE_BIND_HOST` (или `BRIDGE_HOST`), по умолчанию
`127.0.0.1`. Порты: `SOLVER_PORT`, `ROUTE_PORT`, `TELEMETRY_PORT`.
Фронтенд использует соответствующие `VITE_SOLVER_PORT`, `VITE_ROUTE_PORT`,
`VITE_TELEMETRY_PORT` и `VITE_BRIDGE_HOST`.

`SOLVER_PATH` задаёт исполняемый файл solver. `WEB_STATE_DIR` задаёт каталог обмена
с Webots, по умолчанию `web_state`. `MISSION_STATE_DIR` задаёт долговременное
хранилище миссий, по умолчанию `WEB_STATE_DIR/missions`.
Контроллер Webots должен использовать тот же каталог обмена.

На Windows сборка компонентов: `npm run native:build` и `npm run webots:build`.
После изменения `navigation.missionId` требуется пересобрать контроллер.
Отдельные процессы обрабатывают SIGINT/SIGTERM и закрывают ресурсы.

`/ready` planning проверяет наличие solver, route — доступность каталогов.
Готовность сервиса не доказывает подключение или движение робота.

## Состояния и текущие ограничения

`prepared` → `persisted` → `accepted` → `running` → `completed`/`failed`.
Некоторые промежуточные состояния могут быть пропущены между опросами.
`cancelled` зарезервировано контрактом; API отмены миссии сейчас нет.

- Файловый адаптер рассчитан на один процесс записи команд на робота. Распределённой
  блокировки и общей транзакции между несколькими файлами сцены нет.
- Сохранённый снимок миссии неизменен, но текущую сцену симулятора по-прежнему можно
  менять отдельными командами редактора. Это не изолированная среда исполнения миссии.
- Хранилище сохраняет состояния после перезапуска сервиса; автоматического
  восстановления исполнения или повторной отправки при запуске нет.
- Обратная связь считывается при GET миссии. При отсутствии опроса конечное состояние
  можно пропустить, если контроллер уже перешёл к следующей миссии.
- Статус — последнее наблюдавшееся состояние. Файл обратной связи старше пяти секунд
  игнорируется, но ранее сохранённый статус остаётся. Это не индикатор свежести робота.
- UI отслеживает текущую миссию в памяти страницы. Восстановления выбранной миссии
  после обновления страницы и отдельного списка истории пока нет.
- Файлы миссий не очищаются автоматически. Для длительной эксплуатации нужна политика
  хранения; для нескольких писателей потребуется другое хранилище и координация.

## Проверки

`npm test`, `npm run lint`, `npm run build`, `npm run test:webots`,
`npm run webots:build` проверяют клиент, сервисы и контракт контроллера.
`npm run test:services` запускает три отдельных процесса и настоящий native solver,
проверяет отправку, идемпотентность, совпадение ID обратной связи и перезапуск.
Обратная связь в этом сценарии синтетическая: тест не подтверждает физическое
прохождение маршрута в Webots.

Работы с Docker, контейнерами, ядром и обновлением ОС в эту реализацию не входят.
