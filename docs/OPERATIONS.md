# Эксплуатация отдельных сервисов

Webots и gateway размещаются на Windows рядом с файлами симулятора.
Planning, route и telemetry могут работать на другом хосте через `GATEWAY_URL`.
Проверка Ubuntu в CI использует файловые данные вместо физического Webots:
она подтверждает переносимость сервисов и solver, но не Linux GUI симулятора.

## Хранение и резервные копии

Route владеет `MISSION_STATE_DIR/records.sqlite`, gateway —
`WEB_STATE_DIR/gateway-journal/records.sqlite`. Это локальные SQLite-хранилища;
не размещайте их на сетевой файловой системе и не разделяйте между репликами.
Planning и telemetry не требуют собственной постоянной базы.

Перед полной копией завершите или отмените активную миссию, дождитесь остановки
робота, закройте Webots и остановите все сервисы. Не запускайте их до окончания
копирования. Блокировка экспорта обнаруживает работающего владельца базы,
но не обнаруживает Webots и не блокирует весь набор хранилищ одновременно.

Пример из корня проекта с путями по умолчанию (каталог копии должен быть новым):

```powershell
New-Item -ItemType Directory backups/session-01
node scripts/repository-backup.mjs export data/missions backups/session-01/missions.json
node scripts/repository-backup.mjs export web_state/gateway-journal backups/session-01/gateway.json
Copy-Item web_state backups/session-01/web_state -Recurse
```

Проверяйте код завершения каждой команды. Копия считается полной только после
успеха всех трёх операций. Сохраняйте вместе версию приложения, world-файл и
эти три результата. Секреты храните отдельно. Переносите готовые копии на другой
диск; локальная папка `backups` не защищает от потери диска. SHA-256 обнаруживает
повреждение экспорта, но не является подписью: используйте доверенные копии.

Проверка восстановления в новые каталоги:

```powershell
node scripts/repository-backup.mjs import backups/session-01/missions.json data/missions-restored
Copy-Item backups/session-01/web_state web_state-restored -Recurse
node scripts/repository-backup.mjs import backups/session-01/gateway.json data/gateway-restored
```

В скопированном `web_state-restored` замените только `gateway-journal` содержимым
нового `data/gateway-restored` после проверки путей. Исходные рабочие каталоги
сохраните. Укажите `MISSION_STATE_DIR=./data/missions-restored` и
`WEB_STATE_DIR=./web_state-restored`; передайте тот же `WEB_STATE_DIR` Webots.
Запускайте gateway, planning, route, telemetry; проверьте `/ready` и историю
миссий, затем открывайте Webots. Не восстанавливайте только одну базу из другой
даты: журнал доставки и миссии должны соответствовать файлам симулятора.
Восстановление незавершённой миссии может повторить подготовленную команду;
автоматическое продолжение движения после перезапуска Webots не гарантируется.
Поэтому штатные копии делаются при отсутствии активной миссии.

Экспорт не включает таблицу владельца процесса. Импорт проверяет формат,
контрольную сумму и идентификаторы до создания каталога, не перезаписывает
существующие данные. При ошибке записи новый каталог может остаться частичным:
не запускайте из него сервис, повторите импорт в другой новый каталог.

## Секреты и сеть

Задайте один из `GATEWAY_TOKEN` или `GATEWAY_TOKEN_FILE` во всех клиентах шлюза
и самом gateway. Файл — UTF-8, относительный путь считается от корня проекта.
Пустой/недоступный файл и одновременное задание двух вариантов останавливают
запуск. Изменения токена требуют перезапуска клиентов и gateway.
Ограничьте доступ к файлу учётной записью сервисов (Windows ACL / Linux 0600).
`.env`, `secrets/`, `backups/` исключены из Git. Не используйте `VITE_*` для
секретов: эти переменные попадают в браузерную сборку.

Порты route, planning и telemetry пока не имеют пользовательской авторизации.
Оставляйте их на loopback или в доверенной закрытой сети. Для удалённого доступа
нужен защищённый транспорт; bearer-токен gateway сам по себе не шифрует HTTP.

## Логи и завершение

Отдельные entrypoint-процессы пишут JSON-строки в stdout: время UTC, сервис,
уровень, сообщение. Значение gateway-токена и Bearer-значения маскируются.
Не передавайте другие секреты в сообщения. Диагностика самого Node остаётся
в stderr (в том числе ExperimentalWarning для SQLite).

`LOG_DIR=./logs` дополнительно включает файлы каждого сервиса: текущий и три
архива, максимум 5 МиБ каждый. Длинные сообщения обрезаются с `truncated=true`.
Ошибка записи файла сообщается в stdout и не останавливает обработку команд.
Каждый процесс должен иметь собственный файл; не запускайте две копии одного
сервиса с общим `LOG_DIR`. Для общего `npm run bridge` этот логгер не включён.
В будущей контейнерной конфигурации ротация stdout/stderr задаётся средой запуска.

SIGINT/SIGTERM запускают закрытие один раз. Лимит — 10 секунд, после него
процесс завершается с кодом 1. Успешное закрытие не сбрасывает ранее возникшую
ошибку процесса. На Windows принудительное завершение через taskkill не
гарантирует вызов обработчика: используйте Ctrl+C для штатной остановки.
Остановка сервиса не является командой остановки робота: сначала отмените
миссию и дождитесь подтверждения от контроллера.

CI проверяет восстановление миссий после перезапуска и недоступности gateway,
а на Linux — также нулевой код штатного завершения отдельных процессов.
При сбое диска или повреждении SQLite автоматического ремонта нет: остановите
сервисы, сохраните повреждённые файлы для диагностики и восстановите полный набор.
